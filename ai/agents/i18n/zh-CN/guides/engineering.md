# 工程指南

适用于非简单设计、多模块重构、复杂根因调试和设计审查。
本指南遵循全局偏好，绝不扩大授权范围。

## 调查与设计

在最终确定非简单方案、重构、诊断或审查结论前：

1. 先检查受影响的架构、契约、项目清单、测试和运行约束，再形成结论。
2. 聚焦真正主导本次变更的核心约束：状态与资源归属、模块耦合、失败模式和运行约束。
3. 按变更局部性（维护者需阅读、修改和验证的范围）比较可行方案，并在动手前明确验证方式。

## 架构与演进

- 使架构严谨度匹配实际用途（生产服务与内部工具或原型区别对待）；同时避免玩具式脚手架与预设的企业级规模。
- 明确状态和资源归属；仅为具体需求引入服务、异步工作流或分布式协调。
- 面向局部推理优化边界：将因相同原因变更的代码聚拢在一起，用明确契约隔离独立演进的行为，避免同级功能耦合。
- 选择能最小化修改和验证上下文的文件与模块粒度；绝不仅为避免显式接线而引入间接层或动态发现。
- 当保留结构性债务会妨碍达成目标时加以处理，并将兼容性视为权衡而非否决权：对有充分理由的破坏性变更（经授权）规划迁移，仅为具体的上线迁移需求添加适配层或双路径。

## 依赖与 API

- 遵循项目清单与锁文件中声明的运行时和版本约束；当版本升级实质影响设计时加以讨论。
- 当成熟库的收益大于维护、安全、许可证和依赖成本时，优先采用。

## 实现

- 在外部边界将不可信输入解析并校验为带类型约束的结构，使内部代码可信赖不变量；使用内聚对象管理共享状态与生命周期，使用纯函数处理无状态转换。
- 仅当能显著提升清晰度、复用性或可测性时，才将复杂确定性逻辑与 I/O 或框架分离；不要仅为 mock 而给简单调用套上 trait、protocol 或依赖注入包装。
- 保留错误上下文并区分验证、领域、依赖与编程错误；对编程错误和内部不变量破坏快速失败，在信任边界失败即拒绝（除非恢复是有意且安全的）。
- 保持函数聚焦，用早返回保证清晰控制流而非堆砌冗余的防御性卫语句；只为真实共享不变量或具体扩展点提取抽象。
- 明确并发、清理与失败行为，并在完成设计级变更前检查受影响的调用方与契约。
